流水线故障记录系统：第三阶段开发需求
一、目标与范围
在第二阶段项目基础上，实现“用户报修—管理员指派—负责人处理—报修人确认”的完整流程，按时间记录处理过程，并提供 Docker 部署。计划周期为一周，继续使用原来的前后端技术栈和 SQLite，字段、表结构及接口由开发者设计。
二、用户与权限
1. 提供账号密码登录、退出及当前用户信息展示。账号由管理员创建，每个账号选择一种固定角色：普通用户、处理人员或管理员。本轮采用固定角色权限，不增加自助注册、组织架构或自定义权限配置。
2. 普通用户：登记故障，查看自己创建的故障及时间线；在待处理阶段修改基本信息和优先级；确认或退回本人故障的处理结果。
3. 处理人员：查看当前分派给自己的故障及时间线，开始处理、追加进展和提交处理结果。不得处理其他人的任务，也不能自行分派任务或确认完成。
4. 管理员：查看全部故障；在待处理或处理中指定或更换负责人，更换时需填写原因，故障状态和已有处理记录保持不变；在故障完成前调整优先级；管理账号的新增、启用、停用和密码重置。
5. 通常由故障创建人确认处理结果。如果创建人的账号已停用，或旧故障没有对应的创建人账号，管理员可以代为确认或退回，但需填写原因并记录到时间线。已完成的故障和历史记录只能查看；所有角色都不能从数据库中删除故障及其历史记录。
6. 调用业务接口需要先登录。后端应检查用户角色、故障是否由本人创建或分派给本人，以及当前状态是否允许操作，不能只在前端隐藏按钮。创建人和操作人由后端根据登录账号确定。密码使用安全的密码哈希算法保存，不保存明文；账号停用后，即使之前已登录，也不能继续操作。
三、故障处理流程
1. 普通用户登记后进入“待处理”，创建人自动记录为当前用户，优先级默认普通。管理员选择一名启用的处理人员作为负责人；未指派时不能开始处理。
2. 当前负责人点击“开始处理”，故障进入“处理中”；处理中可以多次记录排查和处理进展，每次都要填写说明，不能留空或只填空格。
3. 当前负责人点击“提交处理结果”，填写处理结果后进入“待确认”。创建人点击“确认完成”后进入“已完成”；如未解决，可填写原因并“退回处理”，返回“处理中”，负责人保持不变。
4. 已完成的故障不能改回之前的状态。保留所有处理记录和退回原因；负责人提交结果后，应等待创建人确认，不能自行将故障改为已完成。管理员也应按上述流程操作。


四、处理时间线与交互
1. 详情页展示创建人、当前负责人、优先级、状态，并按时间展示处理过程。至少记录：登记、指派或改派、开始处理、追加进展、提交结果、退回处理、确认完成及优先级调整。
2. 每条记录展示谁在什么时间做了什么，并附上相关说明。更换状态或负责人时，展示修改前后的值。新的处理记录不能覆盖或修改旧记录。修改状态、负责人时，应同时保存对应的时间线记录；其中任何一步失败，都不能只保存另一部分。
3. 页面直接提供“开始处理”“提交处理结果”“确认完成”“退回处理”等按钮，只向用户展示当前有权执行的操作。不再让用户先从下拉框选择状态，再点击“推进状态”。
4. 普通用户默认查看本人报修，处理人员默认查看本人任务，管理员查看全部。保留流水线、状态、优先级组合筛选；管理员另可按负责人筛选，并能查找未分派的故障。列表默认仍按发生时间倒序展示。
5. 同一操作使用相同名称，例如统一使用“新建故障”，不要另一个入口又叫“新建记录”。列表按钮排布清楚，让用户容易找到查看和处理入口，并知道当前等待谁操作。加载中、没有数据、保存成功或失败时都应有提示，提交期间避免重复点击。
五、修复已有问题并检查异常情况
1. 修复时间的时区处理问题：目前在北京时间环境下输入 13:00，保存后会显示成 05:00。保存、刷新页面及重新打开后，都应显示用户原来输入的时间。
2. 修复输入校验问题：必填内容不能只填空格，不能通过提交空格清空已完成故障的处理说明；接口收到 priority: null 等不允许的值时，应返回明确提示，不能报 500 错误。校验不通过时，不应保存错误数据或导致列表无法打开。
3. 检查权限和重复操作：未登录、无权限、故障不存在，或状态已被其他人修改时，应明确提示，不能只保存一部分修改。直接改请求中的故障编号、负责人或创建人，也不能操作无权处理的故障；同一次状态变更不能重复执行或重复记入时间线。
4. 修复首次运行的目录问题：新解压的项目没有 backend/data 目录时，按 README 执行迁移会报错。程序应自动创建目录，或在 README 中明确写出创建步骤，确保照着说明就能完成初始化。
六、数据库升级与历史记录
1. 新增用户、人员关联和时间线等表或字段时，使用 Alembic 升级数据库。既要能从空库建立完整结构，也要能升级第二阶段已有数据库。原故障编号、优先级、处理说明、状态及其他数据都应保留，不能靠删除数据库或重新录入解决。
2. 旧故障如果无法确定对应的创建人或负责人账号，应显示为“历史数据”或“未关联账号”，保留原来填写的处理人名称，不能随意分配给某个新用户。未完成的旧故障由管理员指定负责人继续处理，处理结果由管理员填写原因后确认。
3. 旧的处理说明可以单独显示为“历史处理说明”。如果把它放入时间线，应注明“升级时导入”，不要编造过去由谁、在什么时间做了哪些操作。原来已完成的故障保持已完成。


七、Docker 部署
1. 提供前后端各自的 Dockerfile，以及统一的 Docker Compose 配置。在只安装了 Docker 和 Compose 的电脑或服务器上，按照 README 完成配置后，能够通过 docker compose up -d --build 启动系统，不需要另外安装 Python、Node.js 或配置虚拟环境。
2. 前端容器提供打包后的页面，前后端分别运行在独立容器中，页面能正常调用后端接口。说明访问地址、端口、数据库存放位置和需要填写的配置，浏览器能够完成登录及各项业务操作。
3. SQLite 数据库使用 Docker 数据卷或挂载目录保存，不能只放在容器内部。停止、重新创建容器后，已有数据仍然保留。说明启动和升级时如何执行数据库迁移，多次启动不能清空数据或重复添加演示记录。
4. 提供创建初始管理员的方法，账号和密码可以配置；再次执行时，不能重复创建账号或擅自重置已有密码。不要将真实密码和密钥写死在代码或镜像中。README 说明配置、构建、启动、升级、停止、查看日志和备份数据的方法，并保留前后端本地独立启动说明。
八、成果交付
1. 在原项目上继续开发，完整代码使用 Git 管理。确保提交记录中保留本轮修改前的完整代码，后续按功能或问题修复分别提交，说明每次改了什么。
2. 交付项目压缩包，包含源码、依赖及版本固定文件、Alembic 迁移、Dockerfile、Compose 配置、配置示例、README、必要的初始化代码及完整 .git 目录。交付前自行解压检查 Git 状态和启动步骤。
3. 提供模拟数据和测试账号的准备方法，至少包括两名普通用户、两名处理人员和一名管理员，用来检查能否看到或操作别人的故障。保留第二阶段模拟数据库，用于验证升级。压缩包不包含 node_modules、虚拟环境、缓存、导出的镜像文件或真实业务数据。
4. README 简述角色权限和业务流程，并附简短自检结果及已知问题；不要求另行编写长篇设计报告。
九、验收场景
1. 从干净环境按文档启动 Compose，完成管理员初始化及多账号登录；分别验证空库初始化和第二阶段数据库升级。
2. 普通用户报修，管理员指派，负责人追加多条进展并提交结果，创建人退回一次，负责人再次处理后由创建人确认完成，检查时间线是否完整且状态正确。
3. 验证普通用户不能查看或修改他人故障，处理人员不能处理他人任务或自行确认，普通账号不能管理用户；通过直接请求接口验证，不能只看按钮是否隐藏。
4. 验证改派后旧负责人失去操作权限、新负责人可以继续处理；验证创建人停用后的管理员代确认和历史故障处理路径。
5. 验证非法值、空白说明、重复状态操作及权限失败不会产生错误数据；检查原有筛选、优先级、时间显示和已完成记录保护。
6. 重启及重新创建容器后，账号、故障和时间线数据仍然存在。验收时演示主要流程，并说明后端如何判断谁能操作，以及如何避免只改了故障状态却漏记处理过程。
